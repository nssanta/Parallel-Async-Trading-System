## Обзор Архитектуры

Это **production-ready многопроцессный торговый кластер**, спроектированный для исполнения с задержкой менее секунды на OKX Futures. Система использует распределённую архитектуру, где каждый критический компонент работает в **изолированном процессе** и общается через IPC-очереди (Inter-Process Communication) и HTTP.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           ТОРГОВЫЙ КЛАСТЕР                                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ┌─────────────────┐    Queue     ┌──────────────────────────────────────┐ │
│  │   GATEWAY       │─────────────▶│          BOT MASTER                  │ │
│  │   (FastAPI)     │              │     (asyncio Event Loop)             │ │

│  │  - uvloop       │              │  │  Signal    │  │  Hedge         │  │ │
│  │  - Signal Queue │              │  │  Manager   │  │  Manager       │  │ │
```

### Изоляция Процессов

| Процесс | Роль | Технология |
|---------|------|------------|
| **Gateway** | Приём вебхуков, ингестия сигналов | FastAPI, uvicorn, uvloop |
| **Bot Master** | Оркестрация торговли, управление позициями | asyncio, aiohttp, WebSockets |
| **Scanner** | Тяжёлые расчёты индикаторов | Pandas, NumPy, Binance WebSocket |
| **Telegram** | Уведомления пользователя | python-telegram-bot |

Разделение гарантирует, что **ресурсоёмкие расчёты индикаторов** в Scanner никогда не блокируют **критичную к задержкам торговую логику** в Bot Master.

## Глубокое Погружение: Модель Конкурентности

### Архитектура Event Loop

Bot Master запускает единый **asyncio event loop** (ускоренный `uvloop` на Linux). Все I/O операции неблокирующие, что позволяет системе обрабатывать сотни параллельных операций:

```python
# Упрощённый поток
async def main():
    ws_task = asyncio.create_task(ws_client.start())       # WebSocket стримы
    signals_task = asyncio.create_task(manager.process())  # Обработка сигналов
    balance_task = asyncio.create_task(update_balance())   # Фоновые обновления
    await asyncio.gather(ws_task, signals_task, balance_task)
```

### Изоляция Задач на Уровне Символа

Для **каждой активной позиции** система создаёт **независимые async-задачи**:

```
┌─────────────────────────────────────────────────────────┐
│                    СИМВОЛ: BTC                          │
│  ┌─────────────────┐  ┌─────────────────────────────┐  │
│  │  monitor_task   │  │     hedge_supervisor        │  │
│  │  (Position WS)  │  │  (проверки ROI, TP/SL)      │  │
│  └─────────────────┘  └─────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────┐
│                    СИМВОЛ: ETH                          │
│  ┌─────────────────┐  ┌─────────────────────────────┐  │
│  │  monitor_task   │  │     hedge_supervisor        │  │
│  └─────────────────┘  └─────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

Каждая задача работает со своим **asyncio.Lock** (`symbol_locks[symbol]`), предотвращая race condition при одновременном поступлении сигналов для одного инструмента.

### Hedge Manager: Параллельное Управление Позициями

**HedgeManager** запускает персистентную корутину-супервизор для каждой основной позиции. Она:

1. Мониторит ROI основной позиции через WebSocket данные, пушнутые в Cache
2. Открывает хедж-позиции при пересечении ROI заданных порогов
3. Управляет жизненным циклом хеджа независимо (трейлинг Stop Loss, парное закрытие)
4. Реализует **Safe Zone Logic** для предотвращения whipsaw при повторном входе

```
Основная Позиция (LONG BTC)
    │
    ├── ROI падает ниже -0.5% → Открыть Хедж (SHORT, 0.5x)
    │                               │
    │                               ├── SL сработал → Запомнить цену закрытия
    │                               │                 Ждать выхода из safe zone
    │                               │
    │                               └── Цена вышла из safe zone → Готов к переоткрытию
    │
    └── ROI падает ниже -1.5% → Увеличить хедж (добавить 0.5x)
```

## Уникальные Торговые Механизмы

### 1. Синхронизация REST/WebSocket

Система решает проблему временного рассогласования между REST API ответами и WebSocket потоками данных на уровне биржи:

**Задача**: При размещении ордера через REST API биржа подтверждает операцию мгновенно. Однако WebSocket стрим позиций обновляется асинхронно, обычно в течение 50-500мс.

**Решение**: Система использует синхронизационные задержки для обеспечения консистентности Cache перед выполнением зависимых операций. Эта архитектура предотвращает:
- Дублирование позиций
- Некорректные расчёты усреднения
- Пропуск установки Take Profit

Данный паттерн критически важен для поддержания целостности состояния в высокочастотных торговых средах, где множественные источники данных должны сходиться.

### 2. Оптимистичная Блокировка (Предотвращение Race Condition)

Система реализует **проверки несоответствия состояния** для предотвращения дублирования ордеров при конкурентной обработке сигналов:

```python
# Перед открытием позиции
if (symbol, sig.signal) in open_positions:
    logger.info("Позиция уже существует, отклоняем сигнал")
    return
```

**Поток**:
1. Приходит сигнал на BTC LONG
2. Захвачена блокировка: `async with symbol_locks["BTC"]`
3. Проверка Cache на существующую BTC позицию
4. Если нет → Исполнить вход
5. Если есть → Отклонить сигнал (или обработать как усреднение)

Это предотвращает классический HFT-баг, когда два сигнала для одного символа гонятся открыть дублирующие позиции.

### 3. Приоритет Сигналов и Управление Очередью

Gateway (`Agregator/Server.py`) реализует **ограниченную очередь с вытеснением**:

```python
try:
    signal_queue.put_nowait(sig)
except queue.Full:
    old = signal_queue.get()  # Вытесняем старый сигнал
    signal_queue.put_nowait(sig)
```

Это гарантирует:
- Система никогда не блокируется на ингестии сигналов
- Новые сигналы приоритетнее устаревших при перегрузке
- Память ограничена независимо от потока сигналов

## Установка и Развёртывание

### Локальная Разработка

```bash
# Клонировать репозиторий
git clone <repository-url>
cd FomoDen_v1

# Создать виртуальное окружение
python -m venv venv
source venv/bin/activate  # Linux/Mac
# или: venv\Scripts\activate  # Windows

# Установить зависимости
pip install -r requirements.txt

# Сконфигурировать
cp config.py.example config.py
# Отредактировать config.py с вашими креденциалами

# Запустить
python main.py
```

### Docker Развёртывание

```dockerfile
# Dockerfile
FROM python:3.10-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

CMD ["python", "main.py"]
```

```yaml
# docker-compose.yml
version: '3.8'

services:
  trading-cluster:
    build: .
    restart: unless-stopped
    ports:
      - "8760:8760"  # Порт для Webhook
    volumes:
      - ./state.json:/app/state.json  # Персистентность состояния
      - ./logs:/app/logs
    environment:
      - API_KEY=${API_KEY}
      - API_SECRET=${API_SECRET}
      - PASSPHRASE=${PASSPHRASE}
      - TELEGRAM_TOKEN=${TELEGRAM_TOKEN}
```

```bash
# Запуск через Docker Compose
docker-compose up -d

# Просмотр логов
docker-compose logs -f

# Остановка
docker-compose down
```
